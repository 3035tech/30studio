# 30studio product context

Read this file together with the repository `AGENTS.md` before doing product work. `CLAUDE.md` and `.cursor/rules/30studio.mdc` direct their assistants to the same engineering rules.

## Product

**30studio** is a multi-tenant SaaS marketing workspace. It is one product built with Next.js, not a collection of separate marketing tools. It manages social connections, brand identity, research, content planning and production, media, review, human approval, scheduling, publication, and analytics in one interface.

## Multi-tenant account model

- A customer account is a tenant/organization.
- An organization can own many brands, such as 3035TECH, 30pay, 30grow, 30teach, a personal brand, or brands owned by another future customer.
- An organization can have multiple users. Memberships and invitations connect users to organizations; one user may be a member of multiple organizations.
- Tenant-owned data must be scoped to its organization. Brand-owned data must also reference a brand belonging to that same organization.
- No cross-tenant reads, writes, search, analytics, storage, AI context, logs, caches, or background jobs.
- Server-side authorization resolves the active tenant from a verified session and membership. Client/model/queue-supplied tenant identity is never authoritative.
- Start with explicit roles: owner, admin, editor, approver, and analyst. Roles and permissions are checked in server code for every action.
- Better Auth's organization plugin is the authentication/account provider. The active organization comes from the server-verified session, and each request rechecks its membership in PostgreSQL before doing tenant work. The first role mapping is maintained in application constants and mirrored into Better Auth's access-control plugin; unknown roles fail closed.

## Product decisions

- Core app and workflows live in 30studio. The current first-release recommendation is Next.js plus an internal worker process from this same repository; long-running jobs never run inside UI request handlers. Do not use n8n or Postiz as operational products or sources of truth.
- Social networks are external APIs; their native connectors are modules owned and surfaced by 30studio. Each connector declares its actual capabilities and restrictions.
- PostgreSQL is the source of truth. All application data access goes through Drizzle ORM; application code must not contain raw SQL.
- Portuguese (Brazil) and English are required from the first feature, using `next-intl` and localized message catalogs.
- Build reusable, branded UI components on accessible Radix primitives. Feature pages do not use raw browser controls or library defaults directly.
- The approved 30studio product identity is documented in `docs/PRODUCT_BRAND.md`. Use the supplied logos/icons, Sora + Inter fonts, and Tailwind CSS v4 theme; customer Brand Kits remain tenant-owned and separate.
- Content publication always requires server-verified human approval of the exact content and media version.

## Current implementation boundary

- Better Auth user/session/account/verification, organization, member, and invitation tables are generated by its pinned CLI and included in Drizzle's schema.
- Brands and social-profile metadata have required organization ownership. Social profiles use a composite foreign key so a profile cannot point to a brand from another organization. API repositories require organization scope, and the auth helper checks the active membership and a named permission.
- A first login/signup and workspace/brand entry screen is implemented, including tenant-scoped brand creation, editing, and logical archiving. Team management includes email invitations, verified-email acceptance, role changes/removal, and audit history. SMTP credentials still need to be configured for real email delivery.
- Brand Kits have tenant-and-brand-scoped immutable versions, source URL references, draft/approved/superseded states, manager-only editing/approval, and a version history. Uploaded logos/templates, storage lifecycle, and automated source checks are not implemented yet. Social OAuth/token storage, content versions, approval policies, and publishing remain future slices. It must not be used as a production SaaS until those areas have their own implementation and acceptance tests.
