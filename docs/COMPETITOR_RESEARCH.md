# Competitor research

The collectors support public RSS 2.0 and Atom feeds that a tenant is authorized to use, Instagram Business Discovery for public Business/Creator profiles, public Facebook Page posts, public X profiles and posts when explicitly enabled, and public website metadata. Up to 25 sources can be configured for a brand. Sources and observations are scoped to an organization and brand. The source URL and item link are retained as provenance; each observation records its capture time and retrieval method.

## Collection, analysis, and persistence strategy

Adding a competitor source is asynchronous: the request saves the source and schedules collection; the background worker collects bounded public records, persists observations, and then queues analysis. The interface must tell users that initial results can take a few minutes or longer, depending on worker availability, provider response, and analysis configuration. It must show collection and analysis status instead of implying that adding a source completes research immediately.

PostgreSQL is the source of truth. `competitor_sources` stores the monitored source and its scheduling/health state; `competitor_observations` stores normalized extracted titles, optional summaries, original links, publication/capture timestamps, retrieval method, and analysis state/results; `competitor_fetch_runs` stores bounded operational history. These records always retain organization and brand scope. Archiving a source stops future monitoring but preserves collected observations. Site crawling stores metadata only, never full HTML. Do not place scraped social-network pages in this pipeline as an API fallback: use authorized official APIs or a separately licensed source; use a crawler only for public websites/feeds the tenant is allowed to monitor and whose robots rules permit it.

The worker rejects non-HTTPS feeds, credentials, query parameters, redirects, private or reserved DNS results, unsupported content types, external XML entities, oversized responses, and requests that exceed the timeout. It pins the HTTP connection to a validated DNS address, keeps TLS hostname verification enabled, and does not fetch links found inside feed entries. Feed text is untrusted metadata, never instructions, and is never given to tools. When the configured OpenAI model is available, up to ten bounded public titles and summaries plus the brand name and industry are sent with storage disabled for classification and bilingual idea generation. Source URLs are retained locally for citation and are not included in the model prompt.

Observations contain title, an optional plain-text summary, source link, and source publication date when available. Instagram sources are validated through the official Meta Graph API using a Facebook Page connected to the brand and linked to a professional Instagram account; collection reuses that page's encrypted connection in the worker. Instagram Business Discovery does not cover arbitrary personal profiles. The Meta app must have `instagram_basic` approved, and old Facebook connections must be reauthorized to grant it. Facebook Page sources are validated and collected through the Page Graph API using the brand's connected Facebook Page token. Competitor Page data requires Meta's Page Public Content Access or Page Public Metadata Access approval; without it the provider returns a localized permission state and the worker retries with bounded backoff. Meta recommends system-user tokens for PPCA workloads to reduce rate limiting; the current connector reuses the existing page connection and should migrate to a system-user credential if rate limits or provider review require it. OAuth credentials never enter a worker payload or browser response. The analysis worker assigns a controlled topic, summarizes the observed pattern, and suggests an original editorial angle. Results are stored with the source observation and shown with a citation link. Provider failures retry with bounded backoff; unavailable analyses can be retried by a permitted user. Source monitoring shows health, last/next check time, consecutive failure count, localized error category, and up to eight recent collection runs per source. The database retains at most 50 runs per source. Authorized managers can queue an immediate check when an active source is failing or stale. The worker heartbeat is considered stale after 90 seconds. The dashboard summarizes analyzed, pending, and unavailable observations.

Per-brand in-app alert thresholds default to three consecutive failures and 36 hours since the last successful check. Managers can change them within 1–10 failures and 6–336 hours or disable alerts. The dashboard also groups newly captured posts per source over the last 24 hours and links each alert to its source. Alerts are evaluated when dashboard data is loaded; no email, push, or external notification is sent. Resuming an inactive source clears its failure count.

Competitor trends compare classified observations with a known publication date across the last 30 days and the preceding 30 days. Counts are grouped by the controlled topic taxonomy and the UI links each available trend to a captured observation as evidence. Undated observations are excluded from this comparison. The operational summary reports active sources, sources needing attention, newly captured posts, and pending analyses.

Public-site monitoring accepts a site's HTTPS origin and follows only same-origin sitemap URLs published in `robots.txt` (or `/sitemap.xml` when none are listed). It applies matching `robots.txt` rules, resolves and rejects private/reserved addresses on every request, does not follow redirects, limits each run to two sitemaps and five HTML pages, and extracts metadata only. It does not execute JavaScript, request external links, crawl other subdomains, or store full HTML. This conservative boundary reduces SSRF, resource, and authorization risks; sites without a compatible sitemap or HTML response remain unsupported. `parse5` is used only in the worker/server path to parse bounded HTML according to the HTML Living Standard; it is MIT licensed and compatible with the project's Node 20 minimum. It does not fetch pages or execute scripts. The added `website_crawl` enum value is additive; rollback should revert application behavior and retain the enum value so stored source rows remain readable.

These analyses are advisory suggestions, not verified claims. Engagement counts and LinkedIn social-network collection remain unimplemented. The `metadata_only` data-quality value makes this coverage limit explicit.

## Social network access plan

Treat Instagram, Facebook, LinkedIn, and X as separate provider adapters. The same observation pipeline may be reused after each provider returns authorized, bounded records; do not pretend the RSS adapter can collect their profiles. AI runs only after collection and adds topic/pattern/opportunity analysis, never profile validation, source-of-truth facts, or access to private content.

| Network | Official route and boundary | Delivery gate |
| --- | --- | --- |
| Instagram | Meta's Instagram Graph API exposes Business Discovery for other Business/Creator profiles. It is not a general crawler for every personal profile. | Implemented: connect a Facebook Page with an attached professional Instagram account and `instagram_basic`, resolve a username, show a profile preview, explicitly add it, then collect bounded public media through the existing worker. Requires Meta app permission approval and reconnection of old Facebook tokens. |
| Facebook | Page posts can be read through Graph API, but public competitor Page data requires Page Public Content Access / Public Metadata Access approval. Permissions for a Page the customer owns do not grant general competitor access. | Implemented behind official provider authorization: validate a Page by public ID, username or URL, preview it, confirm inclusion, then collect bounded published posts. Requires Meta PPCA/PPMA approval. |
| LinkedIn | The Posts API requires `r_organization_social` to read organization posts, and LinkedIn restricts this permission to organizations where the authenticated member has an eligible page role. This does not grant access to arbitrary competitor pages; ordinary sign-in and `w_member_social` do not provide that access. | Competitor Page monitoring is unavailable through this permission model. Do not add a connector that presents a customer's managed Page access as authorization to read competitors. Revisit only if LinkedIn provides an approved public competitor-reading product or the product acquires a separately licensed source. |
| X | Public posts and user timelines are exposed by X API v2 subject to current product access, endpoint limits, and developer terms. X states its v2 endpoints are available on pay-per-use plans. | Implemented behind `X_COMPETITOR_RESEARCH_ENABLED=true`: connect an X account with `users.read` and `tweet.read`, validate the public handle through the official API, preview and confirm it, then collect up to 50 recent original posts hourly. Each hourly run makes one timeline API call per source; operators must review current pricing and usage before enabling. The sample environment keeps this disabled. Do not use browser scraping as a fallback. |

Shared acceptance criteria for each adapter: tenant-authorized brand connection, normalized and validated profile identifier, server-side profile preview, explicit user confirmation before saving, encrypted credentials reused from the tenant's connected profile, rate limits and bounded response sizes, idempotent observations with source URL and capture time, explicit permission/coverage errors, and adapter-level capability declarations. Keep unavailable integrations visibly unavailable until the corresponding app access has been granted and verified in the runtime environment.

Official references: [Instagram IG User and Business Discovery](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/), [Facebook Page API requirements](https://developers.facebook.com/docs/graph-api/reference/page/), [LinkedIn Community Management API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview), [LinkedIn Posts API permissions and organization-role boundary](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api), [X API v2 overview and access plans](https://docs.x.com/x-api/overview), [X user lookup](https://docs.x.com/x-api/users/get-user-by-username), and [X timeline pagination guidance](https://docs.x.com/xdks/python/pagination).

`fast-xml-parser` is used for bounded RSS/Atom parsing. It is MIT licensed and runs only in the worker/server path, so it does not add browser bundle weight. The worker polls PostgreSQL using row locks with `SKIP LOCKED`, persists observations idempotently, applies conditional requests, and retries failed sources with bounded backoff. Run it with `npm run worker:competitors` or the opt-in Docker Compose `competitors` profile. Set `OPENAI_API_KEY` and `OPENAI_MODEL` to enable AI analysis; collection still runs without them. Migration `0030` adds collection history, alert settings, and the worker heartbeat. It is additive; an older app version can ignore those tables, so rollback should revert the application without dropping monitoring data.

X calls use the existing server-side bounded-response fetch helper instead of adding another runtime package: the adapter uses two simple X API v2 endpoints, has strict response/time limits, and shares the existing encrypted OAuth connection. This avoids adding a client bundle dependency; operators remain responsible for X usage charges and provider access. Migration `0040` adds the `x_api` retrieval method additively. Keep the enum value on rollback so stored source rows remain readable.
